# Learn2Play release readiness

This runbook is for an authorized release rehearsal. The production database, Storage, Discord, JaaS, and hosting services were not contacted during development. Keep financial approvals disabled throughout rollout and smoke testing.

| Area | Status | Evidence or release gate |
| --- | --- | --- |
| Accounts, roles, evidence and reservations | PASS WITH LIMITATIONS | Local regression suite covers login, pending-provider isolation, evidence authorization, booking and conflicting slots. Verify the intended runtime role and private evidence bucket in staging. |
| Mutual rescheduling | PASS WITH LIMITATIONS | Two-party approval on test data keeps the original slot reserved until acceptance and rechecks conflicts at acceptance. The appointment and payment IDs remain the same. No external notifications are sent. |
| Discord account linking, rooms, and administrator recovery | PASS WITH LIMITATIONS | Fake responses only. Verify callback configuration, test-guild permissions and cleanup procedures before enabling. Discord server owners and administrators can bypass channel overwrites. |
| JaaS meeting authorization | PASS WITH LIMITATIONS | Participant, role, appointment state and payment checks plus signed-token tests are local. Real meeting entry is unverified. |
| Attendance, disputes and gamification | PASS WITH LIMITATIONS | Local regression tests cover attendance races, duplicate XP, disputes and leaderboard. Real disconnect/no-show behavior depends on the existing attendance and dispute workflow. |
| Migration graph and PostgreSQL ledger regression | PASS WITH LIMITATIONS | The source graph has one head, `83ca40c9f279`. Disposable migration and concurrency tests exercise the app's chain. The target PostgreSQL version, revision, locks and grants remain unverified. |
| Target RLS, Storage and role grants | NOT VERIFIED | Require a separately approved read-only inspection and a private staging smoke test. |
| Live payments and provider allocations | BLOCKED | Keep approval disabled until the checks in the financial activation guide pass. No payout or automatic refund is introduced. |
| Public release | BLOCKED | Verify the actual database, services, backups, authorization and configuration before changing hosted services. |

## Configuration review

Vercel rewrites traffic to the Render backend. Render runs Gunicorn with a PostgreSQL connection pool per worker. Confirm the intended public hostname, cookie and proxy behavior, and ability to prevent bypass of any edge authentication throttling through direct Render access. The Flask source does not establish login rate limiting at the edge. Confirm pool size and PostgreSQL READ COMMITTED behavior using the intended staging connection. Keep migrations on a separate owner connection with the privileges required for DDL.

- Flask backend only: `APP_ENV`, `SECRET_KEY`, `DATABASE_URL`. Use distinct test and production credentials and a stable high-entropy session key. Flask uses hashed passwords and CSRF-protected state-changing browser routes. Verify HTTPS cookies, proxy trust, login throttling and callback log redaction.
- Supabase server-side Storage: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `PAYMENT_RECEIPTS_BUCKET` if customized. The service credential must stay on the backend. Evidence and receipt operations check that the configured buckets report private. The avatar bucket has a separate public-image purpose. Audit object policies and signed or public URL paths separately. App authorization checks ownership or administrator authority before sensitive downloads.
- JaaS: `JAAS_APP_ID`, `JAAS_API_KEY_ID`, `JAAS_PRIVATE_KEY`. Confirm separate staging credentials and check participant access while the booking is open and after it closes.
- Discord: `DISCORD_LINKING_ENABLED`, `DISCORD_SESSIONS_ENABLED`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI`, `DISCORD_GUILD_ID`, `DISCORD_BOT_TOKEN`. Begin with both feature flags disabled. Register the exact HTTPS callback and strip query strings from callback logs. Use a separate staging guild with a bot that has the permissions needed to inspect membership, create private voice rooms and manage those rooms. Test hierarchy and permissions in that guild. No standalone bot process or reminder service is required for this port.
- Payment configuration: retain the existing QR/manual workflow and leave `PAYMENT_LEDGER_APPROVAL_ENABLED` unset. Verify the environment's demo designation and receiving account before any later real-payment approval. Demo-mode paid appointments cannot create Discord voice rooms.

## Authorized staging and release sequence

1. Identify and independently verify the target host, database name, PostgreSQL version, Alembic revision and expected Flask role. Record the current app build and cutover window. Verify backups and restore a copy in a disposable environment before applying migrations. Keep credential values out of commands and logs.
2. With separate authorization, run the catalog-only diagnostic using interactive credentials and expected host/database guards described in [Database security diagnostic](database-security-diagnostic.md). Review actual table and sequence grants, RLS and inherited rights for Flask and browser-facing roles, Storage bucket privacy, ledger trigger bindings, ownership and function privileges. Review phase-two functions and receipt revision guards separately. Never apply blanket RLS changes to a shared schema.
3. Rehearse both a fresh disposable PostgreSQL upgrade and an upgrade from the target revision with representative data. Check startup and financial approval still disabled. The named tail of the chain is ledger guard `c83d9f2a71e4`, SQLite-only index repair `db71a6e5c902`, Discord identity `4f78ec3f41a2`, and session coordination `83ca40c9f279`. Verify the optional private tables are visible to the intended Flask role and unavailable to browser roles before enabling. The existing local SQLite file remains at its previously approved revision.
4. Only after authorization, pause affected writes and drain old workers. Apply the reviewed migration under the migration role in the approved environment. Start the compatible app with payments and Discord disabled. Validate health, account sign-in and role boundaries, provider application access, booking and mutual reschedule, old receipt history, and pending versus verified meeting access using seeded records. Smoke-test an assigned participant's JaaS meeting with staging credentials only.
5. On a separate opt-in, validate Discord linking, membership, one room per appointment, denied outsider access, recovery of an uncertain create and idempotent removal. Record who checks for ended rooms and after account or role changes. Discord access can outlive a Learn2Play status change until cleanup. Keep Discord disabled without an operational owner and a cleanup procedure.
6. If deployment verification fails, disable the new flags and restore the last compatible application build after confirming compatibility with the migrated schema. Preserve new audit records, proposals and channels. Forward-fix a migrated database. Database restoration under a reviewed outage plan requires approval and reconciliation of writes since backup. Avoid automatic destructive downgrades.

## Financial safeguards

The existing allocation computes the 20% commission in integer PHP centavos with half-up rounding and assigns the remainder to the provider. Rescheduling only changes the appointment start and proposal history. Approval, refund review, reconciliation and append-only ledger protection remain on their existing paths. Before activation, independently verify trigger-to-function bindings, RLS and runtime grants, historical history and receipt revision safeguards, actual transaction isolation, verification replay, and correction/refund policy with the intended runtime role.
